# Staging setup — what the owner creates and pastes

Everything a human has to create, in order, to bring up `https://staging.<domain>` (docs/DEPLOYMENT.md Step 3).
Code, images and the deploy pipeline are already in the repo; nothing deploys until step 10.

Replace `<domain>` with your domain everywhere. Keep every secret in a password manager; **none of the app secrets go
into GitHub**: they live only in `/opt/pinpulse/.env` on the server. GitHub holds only the SSH deploy key (step 9).

> Costs money: domain, Hetzner server, possibly Neon (see notes). Everything else below has a free tier that covers
> staging. Check current prices on each order page; this runbook does not quote them.

## 1. Domain and DNS
1. Buy the domain (Cloudflare Registrar is at-cost) or move its nameservers to Cloudflare.
2. E-mail addresses `support@<domain>` and `noreply@<domain>`: Cloudflare **Email Routing** can forward both to your
   inbox for free (Email → Email Routing → add the two custom addresses → enable; it adds MX/TXT records itself).

## 2. Hetzner server
1. Hetzner Cloud → new project `pinpulse` → **Add server**:
   - Location **Ashburn, VA (ash)**; image **Ubuntu 24.04**;
   - type with **≥ 4 vCPU / 8 GB RAM** (shared vCPU is fine for staging; web + worker + analytics + Chromium need
     about 3–4 GB, the rest is headroom for image pulls and PDF rendering);
   - IPv4 + IPv6; add **your own** SSH public key; name `pinpulse-staging`.
2. Hetzner **Firewall** attached to the server: inbound TCP 22, 80, 443 and UDP 443 only.
3. On the server as root (one time):
   ```bash
   apt-get update && apt-get -y upgrade && apt-get -y install ca-certificates curl ufw unattended-upgrades
   curl -fsSL https://get.docker.com | sh
   adduser --disabled-password --gecos "" deploy && usermod -aG docker deploy
   mkdir -p /opt/pinpulse && chown deploy:deploy /opt/pinpulse && chmod 750 /opt/pinpulse
   install -d -m 700 -o deploy -g deploy /home/deploy/.ssh
   ufw allow 22/tcp && ufw allow 80/tcp && ufw allow 443 && ufw --force enable
   sed -i 's/^#\?PasswordAuthentication .*/PasswordAuthentication no/' /etc/ssh/sshd_config && systemctl reload ssh
   ```
4. Note the server's **IPv4** and **IPv6** and its SSH host-key fingerprint (Hetzner console → server → or run
   `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` on it) — step 9 needs it.

## 3. DNS records (Cloudflare → DNS), **proxy status: DNS only (grey cloud)**
| Type | Name | Value |
|---|---|---|
| A | `staging` | server IPv4 |
| AAAA | `staging` | server IPv6 |
| A | `mock-oauth` | server IPv4 (only while staging runs MOCK Pinterest; delete at Step 4) |
| AAAA | `mock-oauth` | server IPv6 |

Grey cloud matters: Caddy obtains the TLS certificates itself, and the app trusts only the client IP that Caddy appends
(`TRUST_PROXY=true`); behind Cloudflare's proxy every visitor would look like a Cloudflare IP.

## 4. Neon (Postgres 16)
1. neon.com → **New project** `pinpulse-staging`, Postgres **16**, region **AWS US East 1 (N. Virginia)**, database
   name `pinpulse`. Plan: the Free plan may run out of compute hours because the worker's job queue polls the database
   continuously, so the compute never scales to zero; watch usage in the first week (Launch plan is usage-based).
2. **Connection details → turn "Connection pooling" OFF** (unpooled endpoint; the job queue needs it) → copy the
   connection string for role **`neondb_owner`**. This becomes `DATABASE_OWNER_URL` (migrations only). Use
   `?sslmode=verify-full` and drop `&channel_binding=...` if present.
3. **Do not create `pinpulse_app` in the Neon console.** Roles created there get `BYPASSRLS`, which would switch off
   tenant isolation. The migrations create it with `NOBYPASSRLS`, and refuse to finish if it can bypass RLS.
   You only choose its password: `openssl rand -hex 24`. Then
   `DATABASE_URL=postgres://pinpulse_app:<that password>@<same host>/pinpulse?sslmode=verify-full`.

## 5. Resend (e-mail)
1. resend.com → **Domains → Add domain** `<domain>` (region us-east-1) → add the shown SPF (MX + TXT) and DKIM (TXT)
   records in Cloudflare (DNS only) → **Verify**. Add a DMARC record if Resend suggests it.
2. **API Keys → Create**: permission **Sending access**, domain `<domain>` only → `RESEND_API_KEY` (`re_...`).
3. `EMAIL_FROM="PinPulse <noreply@<domain>>"`.

## 6. Sentry and Better Stack
1. sentry.io → **Create project**, platform **Next.js**, name `pinpulse-staging` → copy the **DSN** → `SENTRY_DSN`.
   One project serves web and worker (events are tagged `component`). Set an alert rule: *a new issue is created* →
   e-mail/mobile; and *event message contains "purge assertion"* → highest priority (a failed purge check).
   Data → Security & Privacy: keep "Data Scrubber" and "Use Default Scrubbers" on (the app already scrubs; this is a
   second layer).
2. betterstack.com → Uptime → two monitors, 3-minute interval:
   `https://staging.<domain>/api/health` and `https://staging.<domain>/api/health/worker` (alerts when the worker's
   heartbeat is older than 3 minutes).

## 7. Pinterest developer app (used at Step 4, created now)
1. Pinterest **business** account → developers.pinterest.com → **My apps → Connect app**. App description: what
   PinPulse does, read-only; privacy policy URL `https://staging.<domain>/privacy` (production domain later).
2. **Redirect URI**: `https://staging.<domain>/api/pinterest/callback` (exact, no trailing slash).
3. Scopes requested by the app: `user_accounts:read`, `pins:read`, `boards:read` only (the app refuses write scopes).
4. Save the **App ID** and **App secret** in your password manager. **Do not paste them on the server yet**: staging
   starts with `PINTEREST_MODE=mock`. Pinterest revokes secrets that leak on GitHub.

At Step 4 the `.env` changes are: `PINTEREST_MODE=live`, `PINTEREST_CLIENT_ID=<App ID>`,
`PINTEREST_CLIENT_SECRET=<App secret>`, `PINTEREST_API_BASE=https://api.pinterest.com/v5`,
`PINTEREST_OAUTH_BASE=https://www.pinterest.com/oauth/`, `INTEGRITY_ALLOW_PRIVATE_HOSTS=false`, remove `MOCK_OAUTH_HOST`
(and its DNS records), then redeploy. **Blocker to know about now:** the app refuses `PINTEREST_MODE=live` with
`BILLING_MODE=simulated` (security review finding 7), so Step 4 also needs the Paddle sandbox (step 8 + the billing PR
that is on hold).

## 8. Paddle sandbox (used when the billing work resumes)
1. sandbox-vendors.paddle.com → sign up (separate from the live account).
2. **Developer tools → Authentication → API keys → New key** → keep as `PADDLE_API_KEY` (not used by the code yet;
   the checkout item is on hold).
3. **Developer tools → Notifications → New destination**: URL `https://staging.<domain>/api/webhooks/paddle`, events
   `subscription.created`, `subscription.updated`, `subscription.canceled` (what `src/modules/billing/paddle.ts` handles) → copy the **secret key** → `PADDLE_WEBHOOK_SECRET`.
4. Products/prices: wait for the pricing decision. When enabling: `BILLING_MODE=paddle_sandbox` +
   `PADDLE_WEBHOOK_SECRET` in `.env`.

## 9. GitHub (repository settings)
1. **Deploy key pair** (on your machine, never reuse your personal key):
   ```bash
   ssh-keygen -t ed25519 -N "" -C "github-deploy pinpulse-staging" -f pinpulse-staging-deploy
   ```
   Append `pinpulse-staging-deploy.pub` to `/home/deploy/.ssh/authorized_keys` on the server (mode 600, owner deploy).
2. **Host key line**: `ssh-keyscan -t ed25519 <server IPv4>` → check the fingerprint
   (`ssh-keyscan -t ed25519 <ip> | ssh-keygen -lf -`) matches step 2.4.
3. **Settings → Environments → New environment `staging`** → *Environment secrets*:

   | Secret | Value |
   |---|---|
   | `STAGING_SSH_KEY` | contents of `pinpulse-staging-deploy` (the private key) |
   | `STAGING_SSH_KNOWN_HOSTS` | the `ssh-keyscan` line from 9.2 |

4. **Settings → Secrets and variables → Actions → Variables** (repository level):

   | Variable | Value |
   |---|---|
   | `STAGING_APP_HOST` | `staging.<domain>` |
   | `STAGING_SSH_HOST` | server IPv4 |
   | `STAGING_SSH_USER` | `deploy` |
   | `STAGING_DEPLOY_ENABLED` | `false` now; `true` in step 10 |

5. Images go to GHCR with the workflow's own token; nothing to create. (Packages stay private.)
6. From Step 1 of DEPLOYMENT.md, if not done: branch protection on `main` (PR + passing `ci`), Dependabot, secret
   scanning with push protection.

## 10. Server `.env` and first deploy
1. Generate the secrets (each command once; paste results into your password manager first):
   ```bash
   openssl rand -base64 32   # BETTER_AUTH_SECRET
   openssl rand -base64 32   # TOKEN_KEK_V1  (also keep a sealed offline copy)
   openssl rand -base64 32   # ANALYTICS_TOKEN
   openssl rand -hex 24      # pinpulse_app password inside DATABASE_URL
   ```
2. On the server as `deploy`: copy `infra/staging.env.example` from the repo to `/opt/pinpulse/.env`, fill every
   `<...>`, then `chmod 600 /opt/pinpulse/.env`.
3. GitHub → set `STAGING_DEPLOY_ENABLED=true` → Actions → **deploy-staging → Run workflow** (ref `main`).
   The run builds images, migrates with the owner role (creating `pinpulse_app`), starts everything and checks
   `/api/health`, `/api/health/worker` and `/privacy`. After this, every green `ci` run on `main` deploys
   automatically. Failures and rollback: `docs/runbooks/deploy-and-rollback.md`.
4. "Done when" (DEPLOYMENT.md Step 3), checked by you:
   - [ ] `https://staging.<domain>` loads, shows the MOCK banner; `/privacy`, `/terms`, `/refunds` show your details.
   - [ ] Browser test against staging from your machine (creates a test user on staging, connects a MOCK account):
     ```bash
     cd apps/web && CHROME_PATH=<path to Chrome> APP_URL=https://staging.<domain> pnpm exec playwright test
     ```
   - [ ] The next morning: Sentry has no new issues; Better Stack green; nightly jobs ran
     (`docker compose -f docker-compose.prod.yml logs worker | grep job.done`).
   - [ ] Backup/restore drill: on hold (docs/runbooks/backup-restore.md).

Rotating: `ANALYTICS_TOKEN`, `RESEND_API_KEY`, `SENTRY_DSN` — change in `.env`, redeploy. `BETTER_AUTH_SECRET` —
signs everyone out. `TOKEN_KEK_*` — add `TOKEN_KEK_V2`, set `TOKEN_KEK_CURRENT=v2`, run `scripts/rotate-kek.ts`
(never just replace V1). The `pinpulse_app` password — change it in `DATABASE_URL` and redeploy; the migration step
applies it.
